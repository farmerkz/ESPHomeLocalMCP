# 🗺 Дорожная карта развития (Roadmap) — ESPHome Local MCP Server

Этот документ содержит структурированный перечень рекомендаций и задач по развитию MCP-сервера для интеграции с **ESPHome Device Builder API**. Формат оптимизирован как для разработчиков, так и для автономной работы AI-агентов (Cursor, Copilot, Antigravity, Claude Desktop, Gemini CLI).

> **Справочная документация:** [ESPHome Device Builder API Reference](https://github.com/esphome/device-builder/blob/main/docs/API.md)

---

## 📊 Текущее состояние

- **Реализовано инструментов:** 27 инструментов (~90% покрытия возможностей API).
- **Базовый стек:** Python 3.11+, FastMCP, websockets, `.env` (TOML-конфигурация).
- **Завершенные фазы:**
  - **Фаза 1 (P0):** Валидация YAML, компиляция, гибкие порты OTA/Serial, параметры `force_local`/`bootloader`, шаблоны плат, онлайн/офлайн переименование, расширенные фильтры плат и управление задачами.
  - **Фаза 2 (P1):** Автомиграция синтаксиса, каталог >940 компонентов и шин, безопасные секреты (`secrets.yaml`), Serial-порты хоста, метки и пакетные операции.
  - **Фаза 3 (P2):** Сетевая диагностика (`troubleshoot_device`), Git-версионирование (`manage_version_history`), AST автоматизаций (`manage_automations`), экспорт артефактов (`get_firmware_binaries`), кластерная компиляция (`manage_remote_build`).

---

## 🎯 Фаза 1: Устранение критических ограничений и доработка существующих инструментов (P0)

Задачи по повышению отказоустойчивости, безопасности и расширению параметров базовых инструментов.

### 1.1. Сквозная сессионная аутентификация (Token / Bearer Auth)

> [!NOTE]
> **Статус:** В текущей реализации авторизация не используется. Доработка механизмов сквозной аутентификации и управления сессиями будет выполнена при возникновении практической необходимости.

- [ ] **1.1.1. Поддержка сохранения токена в `.env` и в памяти сессии**
  - **Команды API:** `auth/login`, `ServerInfoMessage` (`requires_auth: true`).
  - **Описание:** Сейчас при `requires_auth: true` инструменты возвращают ошибку. Требуется реализовать авто-авторизацию: чтение токена или логина/пароля из `.env` / аргументов, отправка заголовка `Authorization: Bearer <token>` или вызов `auth/login` при установлении соединения.
  - **Критерий приемки:** Все 15 инструментов могут успешно выполнять запросы к серверу с включенной аутентификацией.
- [ ] **1.1.2. Добавление команд управления сессией**
  - **Команды API:** `auth/logout`, `auth/refresh`.
  - **Описание:** Реализовать отзыв токена (`auth/logout`) и продление времени жизни токена (`auth/refresh`).

---

### 1.2. Расширение параметров прошивки и компиляции
- [x] ✅ **1.2.1. Гибкий выбор целевого порта/адреса для прошивки**
  - **Команды API:** `firmware/upload`, `firmware/install`.
  - **Инструменты:** `flash_ota`, `compile_and_flash`.
  - **Описание:** Сейчас параметр `port="OTA"` зашит жестко. Добавить возможность передачи:
    - `"OTA"` (по умолчанию)
    - Конкретный IP-адрес или hostname (например `"192.168.1.105"`)
    - Путь к serial-порту (например `"/dev/ttyUSB0"`, `"COM3"`).
  - **Критерий приемки:** Агент может прошить устройство по явному IP или через USB/Serial.
- [x] ✅ **1.2.2. Поддержка параметров `bootloader` и `force_local`**
  - **Команды API:** `firmware/upload` (`bootloader?: bool`), `firmware/install` (`force_local?: bool`, `bootloader?: bool`).
  - **Инструменты:** `flash_ota`, `compile_and_flash`, `compile_firmware`, `batch_compile_and_flash`.
  - **Описание:** Добавить опциональный флаг `bootloader=True` (прошивка bootloader-образа) и `force_local=True` (принудительная сборка локально без offloading).

---

### 1.3. Расширение управления конфигурациями (`manage_device_config`)
- [x] ✅ **1.3.1. Создание устройств по шаблону платы и интеграция с secrets**
  - **Команда API:** `devices/create`.
  - **Описание:** Расширить `manage_device_config(action="create")`:
    - Поддержка параметров `board_id` (генерация конфига из шаблона платы), `friendly_name`, `ssid`, `psk`.
    - При передаче `ssid`/`psk` API сохраняет учетные данные в `secrets.yaml` и использует `!secret wifi_ssid`.
  - **Критерий приемки:** Возможность создать устройство без ручной передачи полного YAML, указав только `name` и `board_id`.
- [x] ✅ **1.3.2. Поддержка онлайн двухшагового переименования**
  - **Команда API:** `devices/rename`.
  - **Описание:** Добавить параметр `config_only: bool = True` (по умолчанию офлайн-переименование файла). При `config_only=False` запускать двухшаговую цепочку: сборка нового конфига → OTA-прошивка старого адреса → атомарная смена файлов при успехе.

---

### 1.4. Расширение каталога плат и управления задачами сборки
- [x] ✅ **1.4.1. Дополнительные фильтры плат в `get_board_info`**
  - **Команда API:** `boards/get_boards`.
  - **Описание:** Добавить фильтры `variant` (esp32c3, esp32s3 и т.д.), `mcu` (rp2040/rp2350), `tag`, `offset`.
  - **Критерий приемки:** Агент может запросить платы по чипу (например `variant="esp32c6"`).
- [x] ✅ **1.4.2. Очистка завершенных задач и отмена отложенных обновлений**
  - **Команды API:** `firmware/clear` (`status?`), `firmware/clear_queued_update` (`configuration`).
  - **Инструмент:** `manage_build_jobs`.
  - **Описание:** Добавить в `manage_build_jobs` действия `action="clear"` (очистка истории задач) и `action="clear_queued"` (сброс staged offline update).

## 🚀 Фаза 2: Новые инструменты для генерации, миграции и конфигурации (P1)

Задачи по внедрению инструментов, упрощающих написание конфигураций и автоматизацию миграций.

### 2.1. Автоматическая миграция устаревшего YAML синтаксиса
- [x] ✅ **2.1.1. Новый инструмент `migrate_device_config`**
  - **Команда API:** `editor/migrate_config` (`{content}`).
  - **Описание:** Инструмент отправляет YAML-конфигурацию в API и получает дифференциальный патч (`YamlDiff`) с автоматической заменой устаревших директив (`services:` → `actions:`, `clk_mode` → `clk`, `rgb_order` → `channel_colors`, `rp2040:` → `rp2:` и др.).
  - **Критерий приемки:** Агент может в один шаг обновить синтаксис устаревшего YAML до актуальной версии ESPHome.

---

### 2.2. Каталог и схема компонентов ESPHome (`components/*`)
- [x] ✅ **2.2.1. Новый инструмент `search_components` / `get_component_schema`**
  - **Команды API:** `components/get_categories`, `components/get_components`, `components/get_component_bodies`, `components/get_pin_registry_modes`.
  - **Описание:** Предоставить агенту доступ к каталогу из >940 компонентов ESPHome:
    - Поиск компонентов по платформе, плате, категории и предоставляемым сервисам (`provides`).
    - Получение точной схемы настроек компонента (`config_entries`), типов полей и ограничений шин (`bus_constraints` для I2C/SPI/UART).
  - **Критерий приемки:** Агент может точно узнать схему любого сенсора/интеграции без риска галлюцинаций параметров.

---

### 2.3. Управление секретами, Wi-Fi и Serial-портами хоста (`config/*`)
- [x] ✅ **2.3.1. Новый инструмент `manage_secrets`**
  - **Команды API:** `config/get_secrets`, `config/set_secret`, `config/set_wifi_credentials`.
  - **Описание:**
    - Чтение списка ключей секретов (без раскрытия приватных данных при get_secrets).
    - Атомарная запись нового секрета в `secrets.yaml`.
    - Быстрая установка Wi-Fi реквизитов (`wifi_ssid` / `wifi_password`).
  - **Критерий приемки:** Агент может безопасно конфигурировать `secrets.yaml` через API.
- [x] ✅ **2.3.2. Новый инструмент `get_host_info` / `list_serial_ports`**
  - **Команды API:** `config/version`, `config/serial_ports`.
  - **Описание:** Получение версий сервера ESPHome/бэкенда и списка подключенных USB-Serial адаптеров (с VID/PID и описанием чипов).

---

### 2.4. Глобальный справочник меток и пакетные операции
- [x] ✅ **2.4.1. Управление справочником меток (`labels/*`)**
  - **Команды API:** `labels/list`, `labels/create`, `labels/update`, `labels/delete`.
  - **Описание:** CRUD-операции над глобальным каталогом меток (создание метки с именем и `#rrggbb` цветом, переименование, удаление с каскадной очисткой устройств).
- [x] ✅ **2.4.2. Пакетные операции над устройствами**
  - **Команды API:** `devices/delete_bulk`, `devices/archive_bulk`, `devices/set_labels_bulk`.
  - **Описание:** Поддержка массового удаления, массовой архивации и массового назначения меток.

## 🔮 Фаза 3: Расширенные возможности, диагностика и Git-версионирование (P2)

Глубокая сетевая диагностика, работа с историей изменений и расширенным инструментарием.

### 3.1. Диагностика сети и доступности устройств
- [x] ✅ **3.1.1. Новый инструмент `troubleshoot_device`**
  - **Команды API:** `devices/troubleshoot`, `devices/get_states`.
  - **Описание:** Глубокая диагностика доступности оффлайн-устройства: одновременная проверка ICMP-пинга, DNS-резолвинга, mDNS/Zeroconf кэша и поиск сетевых аномалий.
  - **Критерий приемки:** Агент может детально ответить пользователю, почему устройство недоступно (проблема mDNS, DNS или потеря IP).

---

### 3.2. История версий конфигураций (Git Version History)
- [x] ✅ **3.2.1. Новый инструмент `manage_version_history`**
  - **Команды / Реализация:** Интеграция с Git-репозиторием конфигураций (`log`, `diff`, `show`, `deleted`, `restore`).
  - **Описание:**
    - Просмотр истории Git-коммитов по конфигурационному файлу или всему каталогу.
    - Просмотр изменений (`diff`) между ревизиями или рабочей копией.
    - Чтение архивного содержимого на выбранном коммите (`sha`).
    - Поиск ранее удаленных конфигураций устройств.
    - Безопасное восстановление и откат файлов на выбранный коммит (`sha`) через API ESPHome.
  - **Критерий приемки:** Агент может просмотреть историю правок YAML и откатить ошибочное изменение.

---

### 3.3. Визуальный редактор и AST автоматизаций (`automations/*`)
- [x] ✅ **3.3.1. Инструменты работы с AST автоматизаций (`manage_automations`)**
  - **Команды API:** `automations/parse`, `automations/upsert`, `automations/delete`, `automations/get_available`, `automations/get_triggers`, `automations/get_actions`, `automations/get_conditions`.
  - **Описание:** Предоставление агенту интерфейса для чтения, валидации и точечной модификации блоков `on_*`, `interval`, `script` и эффектов подсветки без нарушения форматирования файла.

---

### 3.4. Экспорт артефактов прошивки
- [x] ✅ **3.4.1. Новый инструмент `get_firmware_binaries`**
  - **Команды API:** `firmware/get_binaries`, `firmware/download_token`.
  - **Описание:** Получение списка скомпилированных артефактов (`firmware.bin`, `factory.bin`, `firmware.elf`) и генерация токена для скачивания бинарников через HTTP.

---

### 3.5. Кластерная сборка (Remote Build / Offloading)
- [x] ✅ **3.5.1. Управление узлами распределенной сборки (`manage_remote_build`)**
  - **Команды API:** `remote_build/get_settings`, `remote_build/set_settings`, `remote_build/preview_pair`, `remote_build/request_pair`, `remote_build/unpair`, `remote_build/approve_peer`, `remote_build/remove_peer`.
  - **Описание:** Мониторинг и управление сопряжением с удаленными серверами компиляции.

## 🚀 Фаза 4: Расширение возможностей протокола MCP (Prompts & Resources)

Задачи по интеграции специфических возможностей протокола Model Context Protocol для оптимизации работы с контекстом и стандартизации сценариев AI-агентов.

### 4.1. Динамические ресурсы MCP (Context Resources)
- [ ] **4.1.1. Ресурс реестра устройств (`esphome://devices`)**
  - **Описание:** Предоставление живого реестра устройств, IP-адресов, версий и статусов онлайн/офлайн как ресурса MCP для мгновенного считывания контекста моделью без вызова инструментов.
- [ ] **4.1.2. Ресурс прямого чтения конфигураций (`esphome://configs/{configuration}`)**
  - **Описание:** Чтение YAML-конфигураций устройств как URI-ресурсов для контекстного анализа в Cursor/Antigravity (`@esphome://configs/...`).
- [ ] **4.1.3. Ресурсы каталога компонентов и плат (`esphome://components/{id}`, `esphome://boards/{id}`)**
  - **Описание:** Предоставление документации и распиновки компонентов/плат в виде статических/кешированных ресурсов.

---

### 4.2. Интерактивные промпты MCP (Prompt Templates)
- [ ] **4.2.1. Мастер создания устройств (`prompt:new_device_wizard`)**
  - **Описание:** Готовый интерактивный промпт для пошагового проектирования устройства: выбор платы, датчиков, шин I2C/SPI, конфигурации Wi-Fi и валидации.
- [ ] **4.2.2. Промпт глубокой диагностики (`prompt:troubleshoot_offline_device`)**
  - **Описание:** Стандартизированный чеклист автономной диагностики проблем сетевой доступности (DNS ➔ mDNS ➔ ICMP ➔ логи).
- [ ] **4.2.3. Промпт безопасного обновления прошивки (`prompt:safe_firmware_upgrade`)**
  - **Описание:** Сценарий обновления с предварительным созданием Git-точки восстановления, компиляцией, прошивкой и верификацией логов запуска.

## ⚡ Фаза 5: Аппаратный аудит и профилирование памяти (Hardware & Memory Intelligence)

Задачи по предотвращению аппаратных ошибок распиновки и оптимизации микроконтроллерных ресурсов.

### 5.1. Валидация аппаратных конфликтов распиновки
- [ ] **5.1.1. Новый инструмент `validate_hardware_pinout`**
  - **Описание:** Интеллектуальный анализ YAML-конфигурации на предмет аппаратных конфликтов:
    - Попытка использования зарезервированных пинов SPI Flash (например, GPIO6-GPIO11 на ESP32).
    - Конфликты Strapping-пинов при старте (GPIO0, GPIO2, GPIO12, GPIO15).
    - Использование пинов только для чтения (Input-only GPIO34-39) в качестве выходов/ШИМ/I2C.
    - Проверка совпадения адресов I2C на одной шине.

---

### 5.2. Профилирование памяти и размера прошивки
- [ ] **5.2.1. Новый инструмент `analyze_firmware_memory`**
  - **Описание:** Анализ скомпилированных артефактов `firmware.elf` / map-файлов для детальной оценки распределения памяти:
    - Занятость оперативной памяти (I-RAM, D-RAM) и Flash-памяти (Flash Text, RoData).
    - Выдача рекомендаций AI-агенту по оптимизации (отключение лишних логов, сжатие шрифтов, настройка буферов дисплеев).

---

### 5.3. Безопасная Canary OTA-прошивка с автоматическим откатом
- [ ] **5.3.1. Реализация сценария отката прошивки при Bootloop**
  - **Описание:** Двухэтапная прошивка: загрузка бинарника ➔ фоновый мониторинг запуска через `stream_device_logs` ➔ при обнаружении критической паники (Guru Meditation) или перезагрузок автоматический откат на сохраненный стабильный бинарник из `manage_version_history`.
