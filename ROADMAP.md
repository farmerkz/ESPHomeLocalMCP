# 🗺 Дорожная карта развития (Roadmap) — ESPHome Local MCP Server

Этот документ содержит структурированный перечень рекомендаций и задач по развитию MCP-сервера для интеграции с **ESPHome Device Builder API**. Формат оптимизирован как для разработчиков, так и для автономной работы AI-агентов (Cursor, Copilot, Antigravity, Claude Desktop, Gemini CLI).

> **Справочная документация:** [ESPHome Device Builder API Reference](https://github.com/esphome/device-builder/blob/main/docs/API.md)

---

## 📊 Текущее состояние

- **Реализовано возможностей:** 29 инструментов + 4 динамических ресурса + 3 интерактивных промпта (~99.5% покрытия возможностей ESPHome Device Builder API).
- **Базовый стек:** Python 3.11+, FastMCP, websockets, `.env` (TOML-конфигурация).
- **Завершенные фазы и программы:**
  - **Фаза 1 (P0):** Валидация YAML, компиляция, гибкие порты OTA/Serial, параметры `force_local`/`bootloader`, шаблоны плат, онлайн/офлайн переименование, расширенные фильтры плат и управление задачами.
  - **Фаза 2 (P1):** Автомиграция синтаксиса, каталог >940 компонентов и шин, безопасные секреты (`secrets.yaml`), Serial-порты хоста, метки и пакетные операции.
  - **Фаза 3 (P2):** Сетевая диагностика (`troubleshoot_device`), Git-версионирование (`manage_version_history`), AST автоматизаций (`manage_automations`), экспорт артефактов (`get_firmware_binaries`), кластерная компиляция (`manage_remote_build`).
  - **Фаза 4 (MCP Native):** Динамические ресурсы (`esphome://devices`, `esphome://configs/{configuration}`, `esphome://components/{component_id}`, `esphome://boards/{board_id}`) и интерактивные промпты (`new_device_wizard`, `troubleshoot_offline_device`, `safe_firmware_upgrade`).
  - **Фаза 5.1 (Hardware Intelligence, v1.16.0):** Аппаратный аудит распиновки GPIO (`validate_hardware_pinout`), проверка SPI Flash, Input-only, Strapping пинов, повторных назначений и коллизий адресов I2C шины.
  - **Фаза 5.3 (Canary Deployment & Auto-Rollback, v1.17.0):** Безопасная Canary OTA-прошивка (`flash_canary_ota`) со сторожевым мониторингом запуска (Canary Watchdog) и автоматическим откатом при Guru Meditation / Bootloop / Safe Mode.
  - **Программа актуализации API (2026.10):** Полностью завершены **Этап 1** (v1.12.1), **Этап 2** (v1.13.0) и **Этап 3** (v1.14.0) — синхронизированы все 29 инструментов с официальной спецификацией API.

## 🎯 Фаза 1: Устранение критических ограничений и доработка существующих инструментов (P0)

Задачи по повышению отказоустойчивости, безопасности и расширению параметров базовых инструментов.

### 1.1. Сквозная сессионная аутентификация (Token / Bearer Auth)

> [!NOTE]
> **Статус:** Команды управления сессиями (`login`, `logout`, `refresh`) полностью реализованы в инструменте `authenticate_esphome` в рамках Этапа 3 (v1.14.0). Сквозная авто-подстановка токена из `.env` при фоновом подключении ко всем инструментам может быть добавлена при возникновении практической потребности.

- [ ] **1.1.1. Поддержка сохранения токена в `.env` и авто-авторизации в middleware**
  - **Команды API:** `auth/login`, `ServerInfoMessage` (`requires_auth: true`).
  - **Описание:** Сейчас при `requires_auth: true` на защищенном сервере инструменты требуют явного вызова `authenticate_esphome`. Можно реализовать прозрачную авто-авторизацию: чтение токена или логина/пароля из `.env` и автоматический вызов `auth/login` при установлении каждого соединения.
  - **Критерий приемки:** Все 27 инструментов прозрачно выполняют запросы к защищенному серверу без предварительного ручного логина.
- [x] ✅ **1.1.2. Добавление команд управления сессией**
  - **Команды API:** `auth/logout`, `auth/refresh`.
  - **Инструмент:** `authenticate_esphome(action="logout"|"refresh")`.
  - **Описание:** Реализован отзыв токена (`auth/logout`) и продление времени жизни токена (`auth/refresh`) в рамках инструмента `authenticate_esphome` (версия 1.14.0).

---

### 1.2. Расширение параметров прошивки и компиляции
- [x] ✅ **1.2.1. Гибкий выбор целевого порта/адреса для прошивки**
  - **Команды API:** `firmware/upload`, `firmware/install`.
  - **Инструменты:** `flash_ota`, `compile_and_flash`.
  - **Описание:** Сейчас параметр `port="OTA"` зашит жестко. Добавить возможность передачи:
    - `"OTA"` (по умолчанию)
    - Конкретный IP-адрес или hostname (например `"192.168.1.105"`)
    - Путь к serial-порту (например `"/dev/ttyUSB0"`, `"COM3"`).
  - **Критерий приемки:** Агент может прошить устройство по явному IP или через USB/Serial.
- [x] ✅ **1.2.2. Поддержка параметров `bootloader` и `force_local`**
  - **Команды API:** `firmware/upload` (`bootloader?: bool`), `firmware/install` (`force_local?: bool`, `bootloader?: bool`).
  - **Инструменты:** `flash_ota`, `compile_and_flash`, `compile_firmware`, `batch_compile_and_flash`.
  - **Описание:** Добавить опциональный флаг `bootloader=True` (прошивка bootloader-образа) и `force_local=True` (принудительная сборка локально без offloading).

### 1.3. Расширение управления конфигурациями (`manage_device_config`)
- [x] ✅ **1.3.1. Создание устройств по шаблону платы и интеграция с secrets**
  - **Команда API:** `devices/create`.
  - **Описание:** Расширить `manage_device_config(action="create")`:
    - Поддержка параметров `board_id` (генерация конфига из шаблона платы), `friendly_name`, `ssid`, `psk`.
    - При передаче `ssid`/`psk` API сохраняет учетные данные в `secrets.yaml` и использует `!secret wifi_ssid`.
  - **Критерий приемки:** Возможность создать устройство без ручной передачи полного YAML, указав только `name` и `board_id`.
- [x] ✅ **1.3.2. Поддержка онлайн двухшагового переименования**
  - **Команда API:** `devices/rename`.
  - **Описание:** Добавить параметр `config_only: bool = True` (по умолчанию офлайн-переименование файла). При `config_only=False` запускать двухшаговую цепочку: сборка нового конфига → OTA-прошивка старого адреса → атомарная смена файлов при успехе.

## ⚡ Фаза 5: Аппаратный аудит и профилирование памяти (Hardware & Memory Intelligence)

Задачи по предотвращению аппаратных ошибок распиновки и оптимизации микроконтроллерных ресурсов.

### 5.1. Валидация аппаратных конфликтов распиновки
- [x] ✅ **5.1.1. Новый инструмент `validate_hardware_pinout`**
  - **Инструмент:** `validate_hardware_pinout(configuration?, content?, host?, port?)` (реализован в v1.16.0).
  - **Описание:** Интеллектуальный статический и аппаратный анализ YAML-конфигурации на предмет аппаратных конфликтов:
    - Попытка использования зарезервированных пинов встроенной SPI Flash (GPIO6-GPIO11 на ESP32/ESP8266, GPIO12-17 на C3, GPIO26-32 на S3) — вердикт FATAL.
    - Использование пинов только для чтения (Input-only GPIO34-39 на ESP32) в качестве выходов/ШИМ/I2C — вердикт FATAL.
    - Повторное использование одного и того же GPIO несколькими компонентами схемы — вердикт FATAL.
    - Проверка совпадения адресов I2C на одной шине (коллизии адресов) — вердикт FATAL.
    - Конфликты Strapping-пинов при старте (GPIO0, GPIO2, GPIO12, GPIO15) и конфликты ADC2 с Wi-Fi — вердикт WARNINGS.
    - Интеграция с базой распиновок ESPHome `boards/get_board` для извлечения аппаратных примечаний и ограничений.

---

### 5.2. Профилирование памяти и размера прошивки

  - **Инструмент:** `manage_build_jobs(action="analyze_memory")`.
  - **Описание:** Анализ скомпилированных артефактов и профилирование расхода памяти микроконтроллера через нативный вызов API ESPHome:
    - Детализация по компонентам и библиотекам прошивки.
    - Распределение по секциям памяти (Flash/RAM, `.text`, `.rodata`, `.data`, `.bss`).
    - Форматированный Markdown-отчёт с байтами и процентным соотношением (реализовано в версии 1.13.0).

---

### 5.3. Безопасная Canary OTA-прошивка с автоматическим откатом
- [x] ✅ **5.3.1. Реализация сценария отката прошивки при Bootloop**

## 🔄 Актуализация API: Синхронизация с ESPHome Device Builder API (2026.10)

Программа поэтапной доработки сервера на основе ревизии официальной спецификации API Device Builder. Каждый этап выполняется строго последовательно после полного завершения и тестирования предыдущего.

### 🎯 Этап 1: Исправление критических несоответствий и багов интеграции (P0)

- [x] ✅ **1.1. Перевод `manage_version_history` на нативные WebSocket-команды**
  - **Команды API:** `version_history/list_versions`, `version_history/get_version`, `version_history/get_diff`, `version_history/list_deleted`, `version_history/restore`.
  - **Описание:** Замена локальных вызовов CLI `git` (через `subprocess.run`) на удаленные WebSocket-команды ESPHome API с сохранением надежного Git fallback. Обеспечивает полную работоспособность при подключении к удаленным хостам (Home Assistant OS, Docker) и локальным dev-окружениям.
  - **Критерий приемки:** Просмотр истории версий, diff, содержимого и откат конфигурации работают через нативный API ESPHome.
- [x] ✅ **1.2. Корректировка сигнатур и параметров в `manage_remote_build`**
  - **Команды API:** `remote_build/approve_peer`, `remote_build/remove_peer`, `remote_build/unpair`, `remote_build/request_pair`, `remote_build/get_identity`.
  - **Описание:** 
    - Добавлены параметры `dashboard_id`, `pin_sha256`, `receiver_label`, `offloader_label`, действие `get_identity`.
    - В команды `approve_peer` и `remove_peer` передается `dashboard_id` (с fallback на `peer_id`).
    - В команду `unpair` передается `pin_sha256` (с fallback на `peer_id`).
    - В `request_pair` передается полный набор полей, а при отсутствии `pin_sha256` он автоматически запрашивается через `preview_pair`.
  - **Критерий приемки:** Команды одобрения, удаления пиров и сопряжения полностью соответствуют официальному протоколу API.
- [x] ✅ **1.3. Исправление получения паспорта компонента в `search_components`**
  - **Команда API:** `components/get_component_bodies`.
  - **Описание:** В действии `action="get"` реализован запрос полной схемы компонента через `components/get_component_bodies` с выводом параметров `config_entries` (типы, дефолты, обязательность, флаги).
  - **Критерий приемки:** Агент получает полное тело компонента с детальной схемой параметров.
- [x] ✅ **1.4. Нативное атомарное применение AST в `manage_automations`**
  - **Команды API:** `automations/upsert`, `automations/delete`.
  - **Описание:** При `apply=True` передается `save: true` и параметр оптимистичной блокировки `expected` напрямую в API ESPHome без промежуточных вызовов и наложения текстового diff.
  - **Критерий приемки:** Автоматизации сохраняются атомарно на стороне сервера ESPHome.
